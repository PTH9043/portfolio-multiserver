2. 실제 사고를 가정한 5가지 가혹한 실험 결과

실험 1. 만원 방 1,000명 폭주 통과

1,000명이 한 채팅방에 동시에 들어와 채팅 200개(총 20만 건 전달)를 쏟아내고 한꺼번에 나갔습니다. 0.35초 만에 단 1건도 빠짐없이 전달됐고, 서버 메모리는 스마트폰 사진 몇 장 크기인 25.8 MB만 썼습니다.

개발자 메모: 단일 UGameRoom 1,000세션, 200×1,000 SC_CHAT 574,878 pkt/s, p50 164.6ms / p99 293.4ms, 종료 62.5ms (rc=0, stderr=0B).

실험 2. 4개 채팅방 동시 운영 통과

로비·자유·전략·거래 4개 방에 250명씩(총 1,000명) 나뉘어 동시에 채팅 10만 건을 주고받았습니다. 0.19초 만에 완료됐고, 옆 방 대화가 엉뚱한 방으로 섞여 들어간 오류는 0건이었습니다.

개발자 메모: 4개 독립 URoom::_Strand 병렬 처리, 520,291 pkt/s, 방 이동 p99 15.3ms, 교차 오염 0건, Peak RSS 29.7 MB.

실험 3. 방 옮겨 다니기 + 갑자기 선 뽑기 통과

200명이 4개 방을 정신없이 1,371번 옮겨 다니는 도중, 60명(30%)이 방 이동 직후 일부러 인터넷 선을 확 뽑았습니다. 실험 후 남은 인원은 140/140명 정확 일치(유령 인원 0명), 끊긴 60명의 닉네임도 60/60 전부 즉시 재사용 가능했습니다.

개발자 메모: RequestLeaveWithCallback 크로스-스트랜드 전이 + 이동 중 단절 유령 정리 + 전역 UNicknameRegistry RAII 1회 해제 검증.

실험 4. 해킹·방해꾼·잠수 동시 방어 통과

일반 이용자 50명이 대화하는 동안 ① 잘못된·해킹성 요청 100회 ② 느리게 받아 서버를 마비시키려는 방해꾼 5명 ③ 잠수 연결 20명을 한꺼번에 투입했습니다. 방해 요소 125건은 100% 자동 차단됐고, 일반 이용자 50명은 단 한 명도 끊기지 않았습니다.

개발자 메모: 미정의 패킷(999)/깨진 Protobuf/1,021B 초과/중복·규칙위반 100건 차단 + SlowReader 1 MiB 백프레셔 5/5 차단 + 1,000ms steady_timer 유휴 차단 20/20.

3. 어떻게 이렇게 빨라지고 튼튼해졌나요? (쉬운 비유 4가지)

① 편지 1,000번 쓰기 → 1번 써서 복사본 묶어 보내기

전에는 같은 채팅을 1,000명에게 보낼 때 편지를 1,000번 새로 쓰고 우체국에 1,000번 갔습니다. 이제는 편지를 딱 1번만 써서 복사본을 한 묶음으로 보냅니다.

개발자 메모: SHPTR<const BUFFER> 1회 프레이밍 공유 + Boost.Asio Scatter-Gather 배치 async_write.

② 매번 전체 방송 → 0.025초마다 한 번만 모아서 공지

1,000명이 동시에 들어올 때 "1명 입장! 2명 입장!..."을 50만 번 울리던 것을 0.025초마다 최신 인원수 한 번만 깔끔하게 알리도록 고쳐 입장 속도가 44배 빨라졌습니다.

개발자 메모: URoom::_Strand 내부 25ms steady_timer 기반 SC_ROOM_USER_COUNT Coalescing (O(N²) 폭주 제거).

③ 방마다 전담 직원 + 번호표로 즉시 확인

4개 채팅방이 각자 전담 일꾼을 따로 두어 서로 방해하지 않고 동시에 일하며, 복잡한 신분 조회 대신 미리 부여한 고유 번호표로 즉시 대상자를 판별합니다.

개발자 메모: 방별 독립 Strand + 프로젝트 전체 74개 파일 dynamic_cast 7→0건 제거 (TypeID + static_cast, C++20 requires/static_assert).

④ 방해꾼 1MB 차단 + 잠수 연결 자동 정리

데이터를 일부러 안 받아 서버 메모리를 채우려는 방해꾼은 대기 물량이 1MB를 넘기면 즉시 끊고, 30초간 아무 신호가 없는 잠수 연결은 자동으로 정리합니다.

개발자 메모: 송신 큐 1 MiB 백프레셔 + USession 스트랜드 직렬화 steady_timer(_IdleGeneration, 잠금 0) + 클라이언트 10초 CS_PING/SC_PONG.

4. 실험 동안 서버가 사용한 메모리 변화 (실시간 기록 그래프)

사람이 1,000명 몰려들어도 메모리가 끝없이 불어나지 않고 25~30 MB 선에서 안정적으로 유지되며, 사람들이 나가면 연결 자원이 바로 줄어드는 것을 확인할 수 있습니다.

서버가 꺼졌다 켜져도 회원 정보와 출입 기록이 사라지지 않도록 MySQL 8.4 데이터베이스를 실제로 연결해 검증했습니다. 특히 데이터베이스 전담 직원 4명을 따로 두어, 로그인·가입 작업이 진행되는 동안에도 실시간 채팅이 절대 느려지지 않게 분리했습니다.

① 비밀번호는 원본을 절대 저장하지 않습니다

가입한 102명 전원의 비밀번호에 각자 다른 임의 암호 키(솔트)를 섞어 60,000번 변환한 결과만 저장했습니다. 틀린 비밀번호·없는 아이디·같은 계정 중복 접속은 모두 자동 차단됩니다.

개발자 메모: Win32 CNG(bcrypt.lib) 16B CSPRNG 솔트 + 32B PBKDF2-HMAC-SHA256 상수시간 비교, SQL 검증 102/102건 32B/16B 일치, LOGIN_RESULT_ALREADY_ONLINE 차단.

② 서버를 꺼도 마지막 퇴장 기록까지 전부 챙깁니다

서버 종료 버튼을 누르면 먼저 새 접속을 닫고, 데이터베이스 전담 직원 4명이 남은 퇴장 기록(어느 방에서 왜 나갔는지)을 끝까지 저장한 뒤에야 안전하게 종료합니다.

개발자 메모: MariaDB Connector/C 3.4.11 C API + RAII Prepared Statement, UDatabaseManager(UThreadManager 통합 · 스레드당 MYSQL* 1개 · Core.dll DB 무의존), 3단 배수 종료로 connection_logs 미종료 0/102건 달성.

6. 솔직한 한계점과 원본 증거 파일

① 측정 도구의 함정도 직접 교정했습니다: 처음에 가짜 이용자 1,000명을 테스트 프로그램 1개로 돌렸더니 서버는 한가한데도 20.9초가 걸리는 왜곡이 생겼습니다. 테스트 프로그램을 8개 일꾼으로 나눠 다시 정확히 재측정한 결과입니다.

② 현재 단계의 솔직한 한계: 이번 실험은 같은 컴퓨터(Windows PC 1대 + Docker MySQL 8.4) 안의 로컬 통신 기준입니다. 실제 외부 인터넷 환경에서는 통신 거리에 따른 지연(RTT)과 다중 서버 분산 구성이 추가로 고려됩니다. 또한 기존 메모리 기준선(--db=off)과 실DB 모드(--db=mysql)를 언제든 전환해 재측정할 수 있게 유지했습니다.
